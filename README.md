# 共用场地取消预约的容量收益与补救

这里保存共用场地取消预约的容量收益与补救工作所用的匿名合成记录，以及在其上
评估**按单放候补、限量超发、不超发**三种策略的代码。文件不包含居民个人资料。

## 资料

`samples/` 中每个文件都是独立的 UTF-8 JSON 文档：`requests`、`events`、`rooms`、
`assistance`、`decision`。日期是当地日历日期。空值表示没有对应观测或状态资料，
不是数值零。

start/end 为预约区间（半开，分钟），request_minute 是原请求时刻。
events.event_minute 是业务发生时刻，received 是值班可知时刻——回看决策只能使用
`received <= 决策时刻` 的信息。活动区的陪同工位按同时占用计；桌可依 shareable
合并为可互换池。linked_scenarios 给出相互关联的到场组合。replacement 为拟议替代
的场地与区间；accepted_replacement 表示已同意，并以 received 为值班员得知时间。

## 业务口径（代码强制保证）

- 同一次预约可占用相连时段、可合并房间、共用陪同工位；两小时活动区单在其覆盖的
  每个原子时刻都占名额，跨房间冲突用整体可行性判定，**不用逐间空余名额拼策略**。
- 签到延迟与取消是不同事件；`场地停用` 是场地原因，不计居民爽约，也不进风险学习。
- 历史取消不独立：同一带队人会整体改期。已收到改期消息的申请不靠签到学习其当时
  风险；改期单整体从风险样本剔除。改期只有在替代被**实际接受**后才释放原承诺。
- 按接受下一单的时刻做回看，以随后实际签到、拒绝和核对后的空置封账；决策日当天
  截止时刻之后才可知的事件标“待观察”。名单之外的需求只按确有的候补记录计数，
  不凭空加客流。
- 同一组合的多个候补不能都收到确定通知；候补只在开场前、有已确认释放或风险支持
  的预期释放时才可接纳。
- 值班只能从适用策略中确认当日规则；无法守住每场无法入场/等待代价底线、或联动
  到场情景下超容量的策略只停留在比较页面。
- 近开场、无同等替代空间的高损失（protected）预约优先保留。
- 当晚补报后，容量滞留按“预测偏差 / 候补通知太晚 / 组合资源已被另一单占用 /
  场地临时不可用”归因；重算结果只让尚未发出的预约使用。

## 代码结构（`overbooking/`，仅用 Python 3.11 标准库）

| 模块 | 职责 |
| --- | --- |
| `model.py` | 资料装载、交叉校验、房间/陪同工位资源模型 |
| `resources.py` | 可互换池、同组合冲突、整体容量可行性 |
| `timeline.py` | 按 received 组织的可知时刻快照 |
| `risk.py` | 只用历史营业日的爽约概率与释放前置时间（收缩先验） |
| `policy.py` | 三种策略的接单决策 |
| `engine.py` | 逐单回看仿真、候补队列、封账与无法入场重放 |
| `guardrails.py` | 每场无法入场与等待代价底线 |
| `evaluate.py` | 分时段指标、适用性判定、联动到场情景加压 |
| `planner.py` | 营业日规则确认、候补通知、替代释放、重算锁定 |
| `diagnostics.py` | 当晚补报后的容量滞留归因 |
| `backtest.py` | 走查式回测与决策日演练 |
| `report.py` | 命令行报告 |

## 运行

使用 Python 3.11，无需第三方依赖或服务。隔离模式（`-I`）下用仓库根的入口脚本：

```bash
python3 -I run_report.py --samples samples     # 策略比较、适用性、联动、归因报告
python3 -I run_tests.py                        # 全部单元测试与资料关系核对
python3 inspect_samples.py                     # 原始资料盘点（不含业务结论）
```

报告输出的是基于合成资料的比较结果与适用性建议，不自动改写任何预约。
